# PORT-001 — Public demo deployment

## Problem

The public `/demo` route exists, but recruiters do not have a stable HTTPS URL
where they can open it without installing the project. In addition, the root
layout currently subscribes to Supabase authentication on every client route,
including `/demo`, which conflicts with the requirement that the public demo
must work without connected environment variables or external services.

## Evidence

- `src/routes/demo.tsx` contains the complete deterministic journey and imports
  no Supabase client, server function, AI gateway or browser persistence API.
- `src/routes/__root.tsx` calls `supabase.auth.onAuthStateChange` in a root
  effect for every route.
- `src/integrations/supabase/client.ts` throws when its proxy is first accessed
  without Supabase environment variables.
- `npm run build` generates a Nitro `cloudflare-module` worker and
  `.output/server/wrangler.json` with static asset bindings and `nodejs_compat`.
- No public deployment URL is documented in the repository.

## Impact

Without deployment, the main portfolio experience still requires cloning and
local setup. Without isolating the root auth listener, a deployment built with
no connected variables can fail after hydration even though the route itself is
deterministic.

## Decision

Use the existing Cloudflare Workers output produced by Nitro and deploy the
prebuilt application with the generated Wrangler configuration. Add only a
route-aware guard to the root auth listener so `/demo` never initializes the
Supabase client.

The remote AI flow, authenticated routes, database policies and migrations are
out of scope and must remain unchanged.

## Options evaluated

### Cloudflare Workers — selected

- already generated by the current Lovable/TanStack build configuration;
- supports the emitted worker and static asset binding without architecture
  conversion;
- provides stable HTTPS and direct SSR handling for `/demo` refreshes.

### Vercel

- would require adding or changing a deployment adapter despite the current
  build already targeting Cloudflare;
- rejected for this task because it is not the smallest change.

### Netlify

- would also require an adapter/configuration change and new validation;
- rejected for the same reason.

### Static-only hosting

- would require extracting or rebuilding the app as an SPA and adding rewrite
  rules;
- rejected because it changes the existing TanStack Start architecture.

## Files involved

- `src/routes/__root.tsx`;
- `src/routes/demo.tsx` only if a deployment-specific defect is proven;
- deployment metadata generated by the existing build, not manually edited;
- `docs/specs/PORT-001-public-demo-deployment.md`;
- `docs/sessions/2026-07-31-public-demo-deployment.md`;
- `docs/task-board.md`, `docs/testing.md` and `docs/release-checklist.md` after
  deployment evidence exists;
- `README.md` only after a stable URL is validated.

## Acceptance criteria

- [x] stable public HTTPS URL exists;
- [x] `GET /demo` returns a valid page;
- [x] refreshing `/demo` does not return 404;
- [x] no login is requested;
- [x] `/demo` works without connected environment variables;
- [x] the demo makes no request to Supabase or the AI gateway;
- [x] no server secret is present in public JavaScript;
- [x] the journey works in an anonymous browser context;
- [x] the journey works at a mobile viewport;
- [x] the demo can be returned to its initial state;
- [x] production build passes;
- [x] deployment smoke test passes.

## Tests

1. Run `npm run typecheck`, `npm test` and `npm run build`.
2. Start the production preview without `.env` and request `/demo` directly.
3. Inspect browser/network behavior to confirm no request to Supabase or the AI
   gateway during the demo journey.
4. Search generated public assets for known secret names and values without
   printing any secret.
5. After deployment, request `/demo`, repeat the request as a refresh-equivalent
   deep link and check the response status/content.
6. Exercise the five demo steps in an anonymous desktop context and a mobile
   viewport, including returning to the initial step.

An automated Playwright suite is desirable, but adding the test framework is
not required before the first deployment if browser smoke evidence can be
collected during PORT-001.

## Rollback

- roll back the Cloudflare Worker deployment to its prior version or delete
  only the newly created worker if no prior version exists;
- revert the route-aware auth-listener commit with a new commit;
- do not rewrite published Git history;
- remove the public URL from documentation if validation fails.

## Definition of done

PORT-001 is complete only when the URL and all observable deployment checks are
recorded in the session document. A successful local build alone is not enough.
